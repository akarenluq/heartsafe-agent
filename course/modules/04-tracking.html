Nothing slips through

How every escalation is tracked from alert to the patient's action, and who is allowed to move it.

A parcel with a tracking number

A parcel is scanned at every stop, and if it sits too long in one depot someone gets an email. With the platform alone, an alert is more like a letter dropped through a door: if nobody opens it, nobody ever knows.

In the simulation, 924 platform alerts were simply forgotten and never found. With HeartSafe, 853 of the 857 cases that would have stalled were caught by a reminder.

A state machine

A case can only be in one named state at a time, and only certain moves are allowed between them. Engineers call this a state machine. Saying "model this as a state machine with these transitions" gets you far more reliable code from an AI tool than "keep track of the case status".

Only a clinician moves a case

The rule "HeartSafe never decides" is not a promise in a slide. It is enforced in tracker.py: the function that moves a case refuses anyone who is not a clinician.

CODE 
    def act(self, case_id, action, t, actor, role, note=""):        if role != "clinician":            raise PermissionDenied(f"only a clinician can {action} a case")        frm, to = CLINICIAN_ACTIONS[action]        case = self.get(case_id)        if case["state"] != frm:            raise ValueError(f"case {case_id} is {case['state']}, cannot {action}")        if action == "resolve" and not note.strip():            raise ValueError("a resolution note is required")
PLAIN ENGLISH

Move a case one step (acknowledge, review or resolve), recording who did it and their role.

If the person is not a clinician…

…stop with a "permission denied" error.

Look up which state this action moves from and to.

Fetch the case.

If it is not in the right starting state (you cannot resolve a case nobody acknowledged)…

…refuse and say why.

Resolving without a note?

Refuse: a decision must be written down.

Every move is then written to an append-only audit log in a small SQLite database:

CODE 
    def _log(self, case_id, t, actor, role, action, detail=None):        self.db.execute("INSERT INTO audit (case_id, t_h, actor, role, action, detail) VALUES (?,?,?,?,?,?)",                        (case_id, t, actor, role, action, json.dumps(detail) if detail is not None else None))
PLAIN ENGLISH

Write one line to the log: which case, when, who, their role, what they did…

…using an INSERT (add a row), never an UPDATE (change a row)…

…with any extra detail stored as JSON text.

The patient loop: the last mile

A resolved case is not the end. The clinician's decision ("increase the diuretic", "come in for assessment") only helps if the patient acts on it. Here is Mary's loop after her day-50 case:

H
HeartSafe → Mary

Your care team has a plan for you: follow it and tap "confirm" when done. Please also keep your daily readings.

H
HeartSafe

The confirmation deadline passed with no answer. Remote community: maybe no signal. Contacting her caregiver.

C
Caregiver

I'm with her now. Her phone was off. Confirmed: we've read the plan.

H
HeartSafe

Thanks. I'll check her readings 72 hours after she's done it.

H
HeartSafe → Nurse

Readings still show weight gain and breathlessness. Reopening a clinical case for you.

N
Nurse

Seen. Adjusting the plan. (A few days later, on day 66, her readings improve and the loop closes.)

?

Like a case, the loop has its own permission rule: only the patient's side can say "confirmed" or "done".

CODE 
    def patient_step(self, case_id, step, t, actor, role):        """confirm or action_done, recorded by the patient side only."""        if role not in PATIENT_SIDE:            raise PermissionDenied(f"only the patient, a caregiver or a community health worker can {step}")        frm, to, col = {"confirm": ("notified", "confirmed", "confirmed_h"),                        "action_done": ("confirmed", "action_done", "action_done_h")}[step]
PLAIN ENGLISH

Record a patient-side step: "confirm" or "action_done".

(A short description of the function.)

If whoever is recording it is not the patient, a caregiver or a community health worker…

…refuse. The agent can send messages, but never tick the box for the patient.

"confirm" moves notified → confirmed; "action_done" moves confirmed → action_done…

…and each step's time goes in its own column.

Who chases late cases?

In the simulation there are no real nurses, so when a case is created, clinicians.py draws how long the (simulated) nurse takes, and when reminders would fire. The agent then writes those reminders into the tracker:

CODE 
        for t, to in f["reminders"]:            if now + t <= self.horizon:                self.tr.remind(cid, now + t, to)        who = "nurse_backup" if any(to == "backup" for _, to in f["reminders"]) else "nurse_primary"
PLAIN ENGLISH

For each reminder the response model says would be needed (when, and to whom)…

…if it falls inside the 90-day study period…

…record it on the case and in the audit log.

If any reminder went to the backup, the backup nurse is the one who acts.

In a real deployment, a scheduler would instead ask the tracker every few minutes with an SQL query, already written in tracker.due_reminders(): "which cases are past a deadline right now?"

Simulated people, real rules

The nurses and patients are simulated, using response times written as assumptions in config.yaml. But the tracker they act through is the same one the dashboard uses, with the same permission checks. Both HeartSafe and the platform-alone baseline get the same simulated people.
