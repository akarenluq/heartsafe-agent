How HeartSafe Works
01

One patient, one bad week

What HeartSafe does, told through the 90 days of one patient called Mary.

The problem HeartSafe solves

People with heart failure go home from hospital with a scale, a blood-pressure cuff and an app. Every day their readings go to a remote monitoring platform, which raises an alert when something looks wrong.

The platform is good at raising alerts. It is not built to ask "is this reading even real?", to make sure someone acts on the alert, or to notice that patients in remote communities are served worse.

🔍

Check

Is the reading, the ECG or the MRI trustworthy? A wrong scale should not send a nurse running.

📝

Explain

Every escalation comes with a short review: why it was flagged, what can and cannot be trusted.

📦

Track

Each case has deadlines, reminders and a log, and follows the instruction all the way to the patient.

⚖️

Watch fairness

Compares urban, rural and remote patients and proposes fixes when one group falls behind.

💡
A layer, not a replacement

HeartSafe sits on top of an existing platform and reads its feed. This is a common product strategy: instead of rebuilding what works, you add the missing piece around it. When you brief an AI tool, saying "this is an adapter layer over an existing system" changes everything it suggests.

Mary is 68, lives in a remote community, uses her own scale and has a single-lead ECG device. She is the scripted demo patient inside a simulated group of 2,001 patients.

A simulated clock

The code never reads the real time. It uses "hours since monitoring began" so a 90-day study runs in about a minute, and the same seed always gives the same story. Engineers call this a deterministic simulation.

One shared language

The ECG lab, the MRI lab and the agent were built at the same time by different people. That worked because they agreed on one JSON shape for every result, like a standard lab-report form.

prediction, probabilityWhat the model thinks, and how sure it says it is
uncertaintyHow much the model's own parts disagree
qualityIs the signal or image good enough to read at all?
shift_scoreHow different this device or scanner is from the training data
flags, suggested_actionWhat is wrong, and accept / repeat / escalate

Here is the agent reading an MRI result in that shared shape, in reliability.py:

CODE

PLAIN ENGLISH

A function that takes one MRI result, called o.

Get its list of flags, or an empty list if there are none.

Get the scanner details, or nothing if they are missing.

Trust it only if the imaging lab itself said "accept".

Turn each flag into words a nurse understands, and keep any caveats.

Pull out the ejection fraction (how much blood the heart pumps per beat).

Keep the uncertainty, the scanner make and the exam id for the review.

🤝
Agree on the interface first

Because the shape was fixed on day one, the agent could be built on fake "mock" outputs while the real models were still training. When you split work between people or AI agents, write down the data contract first: it is the cheapest way to avoid an integration mess later.

Rules live in the config, not the code

Every clinical number (deadlines, alert limits, assumptions) is in agent/config.yaml, a YAML file. The agent reads it but never changes it.

CODE

PLAIN ENGLISH

Settings for following up on cases.

A nurse must acknowledge a critical case within 4 hours, a caution case within 24, a low one within 72.

The case must be resolved within 48, 120 or 168 hours.

Why this matters

When two cardiologists reviewed the alert rules, nobody had to dig through Python: the changes went into this one file. Ask an AI tool to "move magic numbers into config" whenever experts, not programmers, own the numbers.

Flags plus notes

Every check returns two things: a short machine flag that drives the decision, and a sentence for humans. Ask AI tools for both whenever a system makes a call that a person must later understand.

Step 4: the ECG lab's verdict

The ECG model is a group of five neural networks (an ensemble) trained on hospital ECGs. For each recording it reports quality, uncertainty and a shift score, then makes one of three calls:

CODE 
    def decide(self, q_flags, unc, shift, scale):        flags = list(q_flags)        if unc > self.thr["uncertainty"] * scale:            flags.append("high_uncertainty")        if shift > 1:            flags.append("device_shift")        if q_flags:            return flags, "repeat"        return flags, ("escalate" if flags else "accept")
PLAIN ENGLISH

Decide using the quality problems, uncertainty, shift score and any safeguard adjustment.

Start with the quality problems found so far.

If the model is more uncertain than its calibrated limit…

…flag "high uncertainty".

If the recording is beyond the shift limit (scores are scaled so 1 = the limit)…

…flag "device shift".

Any quality problem?

Then ask the patient to record again: repeat.

Otherwise any flag means a clinician should look: escalate. No flags: accept.

Nothing slips through

How every escalation is tracked from alert to the patient's action, and who is allowed to move it.

A parcel with a tracking number

A parcel is scanned at every stop, and if it sits too long in one depot someone gets an email. With the platform alone, an alert is more like a letter dropped through a door: if nobody opens it, nobody ever knows.

In the simulation, 924 platform alerts were simply forgotten and never found. With HeartSafe, 853 of the 857 cases that would have stalled were caught by a reminder.

A state machine

A case can only be in one named state at a time, and only certain moves are allowed between them. Engineers call this a state machine. Saying "model this as a state machine with these transitions" gets you far more reliable code from an AI tool than "keep track of the case status".

Only a clinician moves a case

The rule "HeartSafe never decides" is not a promise in a slide. It is enforced in tracker.py: the function that moves a case refuses anyone who is not a clinician.

CODE 
    def act(self, case_id, action, t, actor, role, note=""):        if role != "clinician":            raise PermissionDenied(f"only a clinician can {action} a case")        frm, to = CLINICIAN_ACTIONS[action]        case = self.get(case_id)        if case["state"] != frm:            raise ValueError(f"case {case_id} is {case['state']}, cannot {action}")        if action == "resolve" and not note.strip():            raise ValueError("a resolution note is required")
PLAIN ENGLISH

Move a case one step (acknowledge, review or resolve), recording who did it and their role.

If the person is not a clinician…

…stop with a "permission denied" error.

Look up which state this action moves from and to.

Fetch the case.

If it is not in the right starting state (you cannot resolve a case nobody acknowledged)…

…refuse and say why.

Resolving without a note?

Refuse: a decision must be written down.

Every move is then written to an append-only audit log in a small SQLite database:

CODE 
    def _log(self, case_id, t, actor, role, action, detail=None):        self.db.execute("INSERT INTO audit (case_id, t_h, actor, role, action, detail) VALUES (?,?,?,?,?,?)",                        (case_id, t, actor, role, action, json.dumps(detail) if detail is not None else None))
PLAIN ENGLISH

Write one line to the log: which case, when, who, their role, what they did…

…using an INSERT (add a row), never an UPDATE (change a row)…

…with any extra detail stored as JSON text.

Is it fair, and does it work?

Checking the pressure at every tap

A city water engineer cannot just check the average pressure: the average can look fine while the houses at the top of the hill get a trickle. The equity monitor checks each group separately: urban, rural and remote; women and men; age bands; scale type.

When is a gap real?

Small groups bounce around by chance. So each group gets a 95% confidence interval, worked out by bootstrapping, and a gap is flagged only when the whole interval is worse than the overall average.

The machine proposes, a person approves

A gap turns into a proposal: for example "halve the acknowledgement deadline for remote patients", with its evidence and its cost. Nothing changes until an administrator approves it in the dashboard.

Does it work? HeartSafe vs the platform alone

Both arms get the same simulated patients and the same simulated nurses. The only difference is whether HeartSafe sits in between. Numbers from the full run on Nov 9 (2,001 patients × 90 days, real ECG and MRI results):

6.0 h vs 12.5 h

Median time from first alert to acknowledgement, for true heart-failure episodes

86% vs 0%

Alerts caused by faulty readings stopped (another 10.5% held for a nurse check)

853 of 857 vs 0

Cases that would have stalled, caught by a reminder

95% vs 64%

Remote patients who completed the care team's instruction

Say what was assumed

The patients, nurses and response times are simulated from assumptions in config.yaml. The results show the mechanism works under those assumptions, not that it would in a real hospital. Saying this plainly on the slides builds trust with judges.

Spot the bug

Read the numbers, not just the tests

All 12 tests pass, and the code does what it says. The problem only showed up by asking "do these reopenings make sense?" against the ground truth. When an AI tool says "all tests pass", ask it to also check whether the outputs make sense.
